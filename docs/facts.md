# Verified facts

This file holds the facts that the code, the grader or a design choice depends on: about the libraries and tools we pin, and about the graph, the questions and the answer key. Each entry carries evidence a reader re-runs from the repo root, and the date it was last checked. The file is not exhaustive: it holds what was verified when something depended on it, and it grows as such facts are met.

An entry is a heading with its id and the claim, one or two sentences, then the version or source, the evidence, and the date it was last checked.

A new fact takes the next id, goes in the section its subject belongs to (a new `##` section when none fits), and gets one line in Contents. Ids are never reused or renumbered. A fact that no longer holds is corrected or removed in place; the file's git history is the record. When a pinned version changes, re-run the evidence of every entry for that library. To read one entry, search its id with the dot, so that `F1` does not match `F10`: `grep -n '^### F12\.' docs/facts.md`.

## deepagents

### F1. Structured output: `toolStrategy()` with the tool choice left to the model

`createDeepAgent` accepts a `responseFormat`, and the result then carries a typed `structuredResponse`, so the answer shape is enforced by the library instead of requested in the prompt. A bare zod schema does not typecheck (TS2322), although the library's own docstring says it does; wrap it with `toolStrategy(schema)` or `providerStrategy(schema)` from `langchain`.

Neither works as shipped with the current Anthropic models, for opposite reasons. `toolStrategy` binds the schema as a tool and sends `tool_choice: any` on every model call, which Claude Sonnet 5.5, Opus 5.5 and Haiku 5.5 reject (`400 tool_choice: type "tool" and "any" are not supported for this model`). `providerStrategy` sends the schema as the API's `output_config.format`, which constrains every turn to that JSON, and the model, constrained from its first turn, answered `{"answer":"","ids":[]}` without calling a tool. What works: `toolStrategy` plus a middleware whose `wrapModelCall` sets `toolChoice: "auto"` on the request, so the model queries freely and calls the answer tool when done. The structured tool takes its name from the schema's `title` (zod: `.meta({ title })`), `extract-N` otherwise. When the model ends in prose instead, `structuredResponse` is `undefined` and nothing retries; the run record then carries an empty answer, which the eval scores as a failure, and the prompt says the call is required.

- Version: deepagents 1.14.2, langchain 1.5.16, @langchain/anthropic 1.5.12
- Evidence: `grep -n 'structuredTools.length > 0 ? "any"' node_modules/langchain/dist/agents/nodes/AgentNode.js` (the forced choice, overridden by `preparedOptions.toolChoice`); `grep -n "outputConfig: { format" node_modules/langchain/dist/agents/nodes/AgentNode.js` (the provider path); `grep -n "getFunctionName(asJsonSchema.title)" node_modules/langchain/dist/agents/responses.js` (the tool's name); `npm run ask -- dlq-for-prod-2` ends with a `final_answer` call and non-empty ids
- Checked: 2026-10-09

### F5. Known audit finding with no fix: `braces`, via `micromatch` and `fast-glob`

`npm audit` reports a high-severity denial of service (stack exhaustion on deeply nested patterns) in `braces`, which deepagents reaches through `micromatch` in its `glob` and `grep` tools and in filesystem permission rules. Our agent exposes neither tool (see F6) and configures no permission rules, so no pattern the model writes reaches the vulnerable code. Were the tools re-enabled, the exposure would be one failed request, since the agent's filesystem is an in-memory backend scoped to a single run. No patched `braces` exists, and `npm audit fix --force` would downgrade deepagents to 0.0.2, so the finding is accepted.

- Version: deepagents 1.14.2
- Evidence: `npm audit --omit=dev`; `grep -n "micromatch.isMatch" node_modules/deepagents/dist/langsmith-*.js` (every call site sits in a `glob` or `grep` implementation, or in `globMatch`, the permission check)
- Checked: 2026-10-09

### F6. The built-in filesystem tools are replaced, not removed

Passing `tools` to `createDeepAgent` adds to the built-in filesystem tools (`ls`, `read_file`, `write_file`, `edit_file`, `glob`, `grep`); it never removes them. A middleware passed in `middleware` with the same `name` as a default one replaces it, so `createFilesystemMiddleware({ tools: ["read_file"] })` leaves a single filesystem tool; the library requires `read_file` in any explicit list. The `task` tool (the general-purpose subagent) stays. With that, the model sees exactly three tools: `run_cypher`, `read_file`, `task`.

The same replacement applies to the general-purpose subagent behind `task`: its middleware is merged with ours, so it also gets `read_file` alone.

- Version: deepagents 1.14.2
- Evidence: `grep -n "merged.set(middleware.name" node_modules/deepagents/dist/langsmith-*.js` (same-name replacement); `grep -n "must be included in every explicit array" node_modules/deepagents/dist/agent-*.d.ts`; `grep -n "generalPurposeSpec.middleware = mergeMiddlewareStack" node_modules/deepagents/dist/langsmith-*.js` (the subagent); `npm run ask -- "List the exact names of your tools, comma-separated, and call none."` answers `run_cypher, read_file, task` (one small model call)
- Checked: 2026-10-09

### F7. A tool result over about 20,000 tokens is moved to the agent's filesystem

The filesystem middleware measures every tool result; one longer than 80,000 characters (its 20,000-token limit at four characters a token) is written to `/large_tool_results/<call id>.txt` in the agent's in-memory filesystem, and the model receives a short notice with the path and a preview instead, which it can page through with `read_file`. The filesystem tools' own results are exempt. The query tool's row cap keeps its results far below that size, so for `run_cypher` the cap, not the eviction, bounds what the model reads.

- Version: deepagents 1.14.2
- Evidence: `grep -n "toolTokenLimitBeforeEvict = \|toolTokenLimitBeforeEvict \* 4\|large_tool_results/" node_modules/deepagents/dist/langsmith-*.js`
- Checked: 2026-10-09

### F8. Prompt caching is on by default for Anthropic models

`createDeepAgent` adds Anthropic's prompt-caching middleware whenever the model is an Anthropic one, for the main agent and its subagents, so each model call in a run reads the conversation so far from the cache and pays the full input price only on what is new. Nothing in our code turns it on; the run records show it as `cache_read` tokens on every model call after the first.

### F9. Reading the trace: one `AIMessage` per model call, `input_tokens` includes the cached tokens

`agent.invoke(...)` returns `messages`: one `AIMessage` per model call, whose `tool_calls` carry the calls it made and whose `usage_metadata` carries its tokens, and one `ToolMessage` per tool result, linked by `tool_call_id`. In `usage_metadata`, `input_tokens` is the sum of all input tokens, the cached ones included; `input_token_details.cache_read` and `cache_creation` split them out, so the full input price applies only to the difference.

- Version: deepagents 1.14.2, @langchain/core 1.2.17
- Evidence: `grep -n -B2 "input_tokens: number" node_modules/@langchain/core/dist/messages/metadata.d.ts` (the comment says "Sum of all input token types"); after `npm run ask -- dlq-for-prod-2`, each `usage_metadata` in the saved `runs/*.json` has `input_tokens` equal to `cache_creation` plus `cache_read` plus a handful
- Checked: 2026-10-08

### F10. Conversations: a checkpointer, a thread id, and a result that holds the whole thread

`createDeepAgent({ checkpointer })` keeps each conversation's state under the `thread_id` passed at invoke (`{ configurable: { thread_id } }`); the next invoke on that id starts from the stored messages. The result's `messages` is then the whole conversation, every earlier turn included, so a per-turn record reads only the messages from the last user message on. `structuredResponse` is an untracked channel, never written to the checkpoint, so one turn's answer cannot carry over into the next when that turn ends without the answer tool. A turn that dies between a tool call and its result (a deadline, a crash) leaves a dangling call in the thread; the default middleware stack patches it before the next model call, so the conversation stays usable. The same default stack also summarizes a conversation that grows long.

- Version: deepagents 1.14.2, langchain 1.5.16, @langchain/langgraph 1.4.21
- Evidence: `grep -n "checkpointer?: BaseCheckpointSaver" node_modules/deepagents/dist/agent-*.d.ts`; `grep -n "structuredResponse = new UntrackedValue" node_modules/langchain/dist/agents/annotation.js`; `grep -n -B1 "createPatchToolCallsMiddleware()$" node_modules/deepagents/dist/langsmith-*.js` (in the main agent's default stack, after the summarization middleware); with `npm run serve` running, a follow-up such as "Which of those have a Datadog monitor?" posted with the first reply's `threadId` queries the ids of the first answer, and its saved record counts only its own model calls
- Checked: 2026-10-11

## Anthropic API

### F12. The current models take no sampling parameters; effort is the one output knob

`temperature`, `top_p` and `top_k` are refused by Claude Sonnet 5.5 and Haiku 5.5 (`400 invalid_request_error: temperature is deprecated for this model`), as they were from Opus 4.7 on. Thinking is adaptive and on by default, and `output_config.effort` is what sets how much of it the model does. So there is no setting that makes a run deterministic, and none that trades randomness for quality: run-to-run variation is a property of the model, the effort and the prompt, and is measured rather than tuned away. The agent therefore sets `model`, `effort` and `max_tokens` and nothing else, and the eval records those three.

- Version: API `2023-06-01`, models `claude-sonnet-5-5`, `claude-haiku-5-5`
- Evidence: `set -a; . ./.env; set +a; curl -s https://api.anthropic.com/v1/messages -H "x-api-key: $APP_ANTHROPIC_API_KEY" -H "anthropic-version: 2023-06-01" -H "content-type: application/json" -d '{"model":"claude-sonnet-5-5","max_tokens":5,"temperature":0,"messages":[{"role":"user","content":"hi"}]}'` returns the 400; the same request without `temperature` and with `"output_config":{"effort":"low"}` answers
- Checked: 2026-10-10

## TypeScript and NestJS

### F13. `tsx` drops decorator metadata, so the NestJS server runs compiled

`tsx` compiles with esbuild, which ignores `emitDecoratorMetadata`. NestJS's dependency injection reads that metadata, so a Nest app started with `tsx` gets undefined injections. Scripts and tests run with `tsx`; the server runs from `tsc` output or the Nest CLI. A dependency given an explicit token, `constructor(@Inject(ChatService) chat: ChatService)`, needs no type metadata, which is how the endpoint test builds the controller under `tsx`.

- Version: tsx 4.23.15, typescript 6.0.3, @nestjs/testing 12.1.2
- Evidence (metadata): `echo 'const d = (t: any) => t; class A {} @d class B { constructor(a: A) {} }' | node_modules/.bin/esbuild --loader=ts --tsconfig-raw='{"compilerOptions":{"experimentalDecorators":true,"emitDecoratorMetadata":true}}' | grep -c __metadata` prints 0; the same source through `npx tsc --ignoreConfig --experimentalDecorators --emitDecoratorMetadata` emits `__metadata` calls
- Evidence (`@Inject`): `npm test` passes `src/server/chat.controller.test.ts`, which builds the controller under `tsx`; with the `@Inject(ChatService)` removed, its valid requests answer 500
- Checked: 2026-10-11

From version 12 the Nest packages are ESM (`"type": "module"`), like this package, so the server imports them directly and compiles with the same `NodeNext` settings as the rest of the code. ## Neo4j

### F17. A read-mode transaction refuses writes on the server

`executeQuery(query, {}, { routing: neo4j.routing.READ })` runs the query in a read transaction, and the server rejects any write inside it (`Neo.ClientError.Statement.AccessMode`, "Writing in read access mode not allowed"). That makes the agent's query tool read-only without inspecting the query text. The fixture runs the Community edition, which has no read-only users or roles, so the transaction mode is the guard.

- Version: neo4j-driver 6.2.0, Neo4j 2026.04.0 Community
- Evidence: `docker compose exec -T neo4j cypher-shell -u neo4j -p neo4j --access-mode read "CREATE (x:Probe) RETURN x"` fails with "writing in read access mode"; `docker compose exec -T neo4j cypher-shell -u neo4j -p neo4j "CALL dbms.components() YIELD edition RETURN edition"` prints `community`
- Checked: 2026-10-08

### F18. Unknown labels and relationship types are warnings, not errors

A query that names a label or relationship type absent from the database still runs and returns no rows; the result summary carries a notification with `severityLevel` `WARNING` (`Neo.ClientNotification.Statement.UnknownRelationshipTypeWarning` or `UnknownLabelWarning`) whose description names the missing one. The query tool forwards these warnings so that a misspelling is not read as an empty answer. Deprecation notices arrive the same way at a lower severity and are dropped.

- Version: neo4j-driver 6.2.0, Neo4j 2026.04.0
- Evidence: `curl -s -u neo4j:neo4j -H 'Content-Type: application/json' -d '{"statements":[{"statement":"MATCH ()-[:NOPE]->() RETURN count(*)"}]}' http://localhost:7474/db/neo4j/tx/commit | grep -o '"code":"[^"]*"'` lists the `UnknownRelationshipTypeWarning`
- Checked: 2026-10-08

### F19. A permission reaches a bucket only through the bucket's policy

Every node carries the label `Entity` plus one resource label (29 in all), and 579 relationships of 30 types connect them. An IAM policy's `GRANTS_ACCESS_TO` points at queues, databases and bucket policies, never at a bucket; the bucket is one hop further, `(:AwsS3BucketPolicy)-[:APPLIES_TO]->(:AwsS3Bucket)`. So the access chain from an instance is `USES_INSTANCE_PROFILE`, `ASSUMES_ROLE`, `ATTACHED_POLICY`, `GRANTS_ACCESS_TO`, plus `APPLIES_TO` for a bucket, and a query that looks for `:AwsS3Bucket` at the end of `GRANTS_ACCESS_TO` finds none. The key follows the same chain: "Trace how i-ecomm-prod-01 reaches its S3 bucket." expects six ids, the bucket policy among them.

- Source: `mock-infra.cypher`; the live graph; `eval/expected.generated.json`
- Evidence: `docker compose exec -T neo4j cypher-shell -u neo4j -p neo4j "MATCH (a)-[r]->(b) RETURN [l IN labels(a) WHERE l <> 'Entity'][0] AS from, type(r) AS rel, [l IN labels(b) WHERE l <> 'Entity'][0] AS to, count(*) AS n ORDER BY rel, from"` lists the schema as 50 (from, type, to) rows; `docker compose exec -T neo4j cypher-shell -u neo4j -p neo4j "MATCH (n) RETURN size(labels(n)) AS labels, count(*) AS nodes"` prints `2, 297`; `docker compose exec -T neo4j cypher-shell -u neo4j -p neo4j "MATCH ()-[:GRANTS_ACCESS_TO]->(x) RETURN [l IN labels(x) WHERE l <> 'Entity'][0] AS kind, count(*) AS n ORDER BY kind"` prints `AwsRdsInstance 12`, `AwsS3BucketPolicy 12`, `AwsSqsQueue 24`; `node -p 'require("./eval/expected.generated.json").evals["path-compute-to-s3"].expected_resource_ids'` lists the six
- Checked: 2026-10-12

### F20. An id's last segment is not always the resource's name

For 32 nodes the `id` does not end with the `name`: the 12 bucket policies (`aws:s3-policy:bucket-commerce-prod-1` is named `bucket-commerce-prod-1-policy`), the 12 Datadog monitors (`datadog:monitor:commerce-1` is `commerce-prod-monitor-1`) and the 8 workflows (`github:workflow:repo-commerce-prod-1:deploy-prod` is `repo-commerce-prod-1/deploy-prod.yml`). The key lists ids, so an answer cites the `id` property, never a name. And since each bucket policy's id ends with its bucket's name, the grader, which recognises a resource the question names by the last segment of its id, treats both the bucket and its policy as named in "Which compute instances can reach bucket-commerce-prod-1?".

- Source: the live graph; `eval/score.ts` (`namedInQuestion`)
- Evidence: `docker compose exec -T neo4j cypher-shell -u neo4j -p neo4j "MATCH (n) WITH n, split(n.id, ':') AS p WHERE p[size(p)-1] <> n.name RETURN [l IN labels(n) WHERE l <> 'Entity'][0] AS kind, count(*) AS n, collect(n.id)[0] AS id, collect(n.name)[0] AS name ORDER BY kind"` prints the three kinds with 12, 12 and 8; `grep -n -A4 "function namedInQuestion" eval/score.ts`
- Checked: 2026-10-12

### F21. The answer key is generated by a script outside this repository

`eval/expected.generated.json` names its generator, `eval/tools/truth.ts`, which is not in the repository, so the query behind each expected set is known only from the set itself. The file holds the 30 question ids of `eval/QUESTIONS.md`, each entry's `count` equals the length of its list, and every expected id exists in the seeded graph. Each set is therefore exact for its generator's reading of the question; where the English allows another reading, the set shows which one it took (the next two entries). Ten questions name a resource. The key leaves it out of the expected set in nine ("Where do failed messages from queue-commerce-prod-2 go?" expects `queue-commerce-prod-14` alone) and includes it in one, the path question ("Trace how i-ecomm-prod-01 reaches its S3 bucket." starts with `i-ecomm-prod-01`).
