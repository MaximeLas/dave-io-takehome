# The improvement loop

*The improvement loop step by step, its prior art, what it does not avoid, what is validated, its first two runs, and the eval page it runs from; the write-up's summary is in [`SOLUTION.md` § What comes next](../SOLUTION.md#what-comes-next).*

Today a failing question is diagnosed by reading its trace by hand, which is how the business-area failure was found (the agent found an area's resources, then dropped them). The loop makes that diagnosis repeatable, in five steps:

1. **Re-derive the key.** Done: [`eval/key-overlay.json`](../eval/key-overlay.json) amends the one answer the audit finds wrong, and `npm run eval` reports the score against both.
2. **A reference file** holding the reasoning and the evidence behind each answer. Done: [`eval/key-audit.md`](../eval/key-audit.md), thirty entries, each with its reading, its query and its verdict.
3. **A judge** that reads one failing trace against that reference and names where the reasoning went wrong. Built, not validated: `npm run improve` ([`src/improve/`](../src/improve/)) hands the earliest failing trace of each question that failed a trial to a judge, Claude Opus 5.5, with the agent's own prompt and tools, the question, the expected ids, the question's audit entry and the trace in numbered steps. It names the step of the first error, quotes the instruction that governs that step and says whether the agent did not follow it or followed it into the error, and tags the trace with seven failure modes. One of them is "the key is at fault": a miss the audit blames on the key or on an ambiguous question is named rather than turned into a change, and the judge may dispute the audit itself with evidence from the trace, since the audit is one re-derivation, the reference rather than an oracle.
4. **An aggregator** that reads the judge's reports and proposes one change. Built in the same command: one more call reads every judgement beside all the experiment files and proposes one change to the prompt, a convention, a tool's description, the model or the effort, or no change when the misses are the key's, what is left is noise, or the traces are too few to show a pattern. A proposal carries the failure pattern, the hypothesis, what might regress, what was already tried, and a check written before any run: the one thing a new trace must show in every trial if the hypothesis is right. At three trials a question's pass count mostly moves within the noise, so that check is how a proposal is judged beyond its score. The proposal goes to `runs/improve/` with the eval record's id, the run ids judged, the agent's fingerprint and the improver's own model and prompt hash, and it changes nothing: a person picks, and the eval measures the change like any other ([decisions](decisions.md#why-an-improver-that-proposes-and-never-applies)).
5. **The loop on demand.** Built as a command, `npm run improve`, and as a page: the eval page runs the eval, shows each failure with its trace and hands the failing questions to the improver at a click ([the eval on a page](#the-eval-on-a-page)); each button's first paid run is recorded there. Running it in CI is not built. A faster loop on the same thirty questions makes fitting them easier, which the paragraph below on fitting the thirty applies to the page as much as to the command.

**Prior art.** Optimising a prompt automatically against a metric is an established line of work, with libraries: DSPy's optimisers such as MIPROv2, and GEPA ([Agrawal et al., 2025](https://arxiv.org/abs/2507.19457)), which reflects in natural language on its own failed attempts to rewrite a prompt. Model judges reading traces are standard practice, and LangSmith's [Insights](https://docs.langchain.com/langsmith/insights) groups traces into categories of behaviour and failure. Borrowed here: the judge, the grouping of failures into one pattern, the reflection in words rather than a search over prompts. Specific here: each trace is read against a per-question reference derivation (the key audit) with the agent's own prompt, tools and past experiments in context, and a miss the audit blames on the key is named instead of fixed.

**What it does not avoid: fitting the thirty.** A change taken from this loop is diagnosed on the thirty questions and measured on them, as an optimiser's would be, and the improver reads each question's audit entry, which holds the query that returns the expected set. A sentence worded generally can still be fitted to the thirty, and a person reading it cannot see that it was. The difference from DSPy or GEPA is selection pressure, not measurement: they search many candidates and keep the winners of a noisy score, while a round here puts forward one hypothesis, its check written before the run, under the conventions' rule that a line states something about the domain. That lowers the odds of keeping noise; it does not detect a fit. Only the held-out set in [item 3](../SOLUTION.md#what-comes-next) can, and the improver must never be shown it.

**What is validated and what is not.** The command's code is tested without a model call: which traces are chosen, what the judge is shown for a fixed record, the refusal of traces from another agent, the proposal's shape with a change and without one, and a failed call keeping the judgements that landed. It prints its estimated cost before the first call. The judge is not validated: no person has labelled failing traces for its failure modes, so its true positive and true negative rates are unknown, and like the judges placed in [where a judge would enter](metrics.md#where-a-model-judge-would-enter-and-why-none-gates) it proposes and never gates. A proposal is a hypothesis for a person to check against the traces it cites.

**An example of its output, not evidence that the judge is right.** The first full run (13 Oct, Claude Opus 5.5 at effort high, 89 cents, on an earlier version of the improver's prompt, `97ad4cb1`, before the no-change outcome and the written check were added) read the eval record of the current baseline's accept (Haiku 5.5 at effort high, prompt `1d555744`), one failing trace from each of the six questions that failed a trial:

- **The pattern it named:** in "What should I inspect if fulfillment jobs are backing up?" and "Which instances can connect to rds-commerce-prod-4?", the agent's own queries reached the set the conventions point to and its `ids` then took another layer's resources. It proposed one sentence in the `ids` rule: when two layers disagree about what uses, reaches or watches something, the ids come from the layer the conventions assign to that verb.
- **What it left out:** the storefront question (the audit calls it ambiguous) and the order-flow question (the key's error), which is what the key-at-fault tag is for.
- **As a Claude agent reviewing the command read it:** the proposal's "before" text matches the prompt exactly, and its prediction called the database question's move alone within noise and named what a trace would have to show instead (the fulfillment answer swapping in the right four instances in every trial). Against that, the pattern rests on one trace from each of two questions; two tags, a different reading of the question and an instruction not applied, were each true on four traces of six, so neither discriminated; and an earlier run on one question named step 0 of a trace whose steps start at 1, found the same error in substance that the full run placed at step 9, and proposed a different change from that narrower input. A step outside the trace is now refused. Nothing it proposed is applied or measured.

The second full run (13 Oct, the same model and effort, on the shipped improver prompt `6731721c`, 57 cents, from the eval page) read a one-trial record of the same agent with three failing questions, the known three, and proposed no change: it read the storefront miss as the audit's own second reading of an ambiguous question, the order-flow miss as the key's error, and the fulfillment miss as one question with one trace whose only fix in view would be a line fitted to that question's wording, which the business-area experiment had declined to add; it named instead the evidence that would justify a change, several differently worded troubleshooting questions on a held-out set, or the same choice repeated across trials. That is the outcome the no-change option was added for. One run each way says nothing about how often the judge is right.

## The eval on a page

`npm run serve` also serves `eval.html`: an eval record as one table, a row per question with its text, its passes beside the baseline's, the ids missed and added in each failing trial and a link to each trace, under the verdict the record stored when it was judged. Buttons run one question, the whole eval and the improver through the functions the commands call; none can move the baseline or apply a proposal ([decisions](decisions.md#why-a-page-over-the-eval-and-why-can-it-not-move-the-baseline)). The [screenshot](eval-page.png) is the key audit's three-trial run (eval id `2026-10-12T21-56-13-511Z`, commit `40c1a95`, prompt `1d555744`, 26, 26 and 27 passes), filtered to its four questions that failed a trial, under the verdict it stored against the baseline of its time (commit `268529c`: mean 25.7 passes, 25 solid questions), not against today's. The page was built by a Claude agent and its endpoints are tested without a model. Its buttons that spend first met a key whose spend cap was reached, which each reported in one line; then, on 13 Oct with the cap raised, each made its first paid run on the shipped agent (prompt `1d555744`, agent `a6d81ecf`): one question (the rds-commerce-prod-4 access question, a pass, every id grounded, 0.35 cents), one eval trial (eval id `2026-10-13T09-21-34-260Z`, 27 of 30 and 28 against the amended key, 9.2 cents, reported and not compared, as the command reports one trial; the three misses the known ones, storefront, order-flow and fulfillment backing up), and the improver on that trial's three failing questions (57 cents: three judge calls and one proposal), which proposed no change, reading two misses as the key's or the question's by the audit's own verdicts and the third as one question with one trace, and named the evidence that would justify a change. One run of each proves the path, not the page.

The next layer is a workbench on the same page: edit one of the inputs it already lays out (a prompt line, a tool's description, the effort) without saving, run the thirty on the edited agent, and read the result against the baseline, so a proposal is tried before anyone commits it. The record would carry the edited agent's version, which no committed code produces, so such a run could inform a change and never be accepted.
