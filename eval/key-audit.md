# The answer key, audited

`eval/expected.generated.json` lists the expected ids for each of the thirty questions, generated by a script that is not in this repository ([F21](../docs/facts.md#f21-the-answer-key-is-generated-by-a-script-outside-this-repository)). This file re-derives every answer from the graph: for each question, the reading applied, the Cypher query that derives the answer, the ids it returns, and a verdict against the key. A Claude agent (Claude Opus 5.5) wrote it on 13 Oct 2026, from the live graph seeded by `mock-infra.cypher`, reading the questions and the key, with the vocabulary of the agent's conventions (`src/agent/conventions.ts`): "reach", "access" and "connect" as permission, storage and data as buckets and databases, and a business area by each resource's own description, in both environments unless the question names one.

The evidence is the query, not the agent that wrote it. Every query returns one column, `id`, and runs as pasted against the seeded database: in the Neo4j browser at http://localhost:7474, or with `docker compose exec -T neo4j cypher-shell -u neo4j -p neo4j "<query>"` (the credentials in `.env.example`).

**The verdicts.**

- **Agrees:** the reading a user most plausibly means returns the key's set exactly.
- **Disagrees:** the key's set is reproduced by a query whose reading is named, and the audit argues why a different reading is the right one for the question as asked.
- **Ambiguous:** the wording supports two readings, both queries are shown, and the entry says which one the key took.

The amendments live in [`eval/key-overlay.json`](key-overlay.json): every **disagrees** entry, and an **ambiguous** one only where the audit finds the key's reading the weaker (none is). The key file is never edited.

### `fulfillment-backing-up`

> What should I inspect if fulfillment jobs are backing up?

**Reading.** Fulfillment jobs wait in the queues described as fulfillment work (`queue-commerce-prod-5` to `-8`, "fulfillment-adjacent work"). To inspect a backlog: those queues, their dead-letter queues if any, the monitors that watch them, and the compute permitted to read them, found by following the graph from the queues, as the conventions say for "what uses, reaches or watches something".

```cypher
MATCH (q:AwsSqsQueue) WHERE toLower(q.description) CONTAINS 'fulfillment'
OPTIONAL MATCH (q)-[:REDRIVES_TO]->(d:AwsSqsQueue)
OPTIONAL MATCH (m:DatadogMonitor)-[:MONITORS]->(q)
OPTIONAL MATCH (i:AwsEc2Instance)-[:USES_INSTANCE_PROFILE]->()-[:ASSUMES_ROLE]->()-[:ATTACHED_POLICY]->()-[:GRANTS_ACCESS_TO]->(q)
WITH collect(DISTINCT q.id) + collect(DISTINCT d.id) + collect(DISTINCT m.id) + collect(DISTINCT i.id) AS ids
UNWIND ids AS id
RETURN DISTINCT id ORDER BY id
```

Returns 10: `aws:ec2:i-ecomm-prod-02`, `aws:ec2:i-ecomm-prod-06`, `aws:ec2:i-ecomm-prod-10`, `aws:ec2:i-ecomm-prod-14`, `aws:sqs:queue-commerce-prod-5`, `aws:sqs:queue-commerce-prod-6`, `aws:sqs:queue-commerce-prod-7`, `aws:sqs:queue-commerce-prod-8`, `datadog:monitor:commerce-5`, `datadog:monitor:commerce-6`

**Verdict: agrees.** The four instances are described as product-information hosts, which makes the set look wrong at first sight; they are the only compute whose permissions reach the fulfillment queues. The reading not taken lists the fulfillment area by description instead: the instances described as fulfillment workers (`i-ecomm-prod-04`, `-08`, `-12`, `-16`), the fulfillment databases and the queues. Those workers' permissions reach the four dead-letter queues and none of the fulfillment queues. That other reading is a legitimate diagnostic path too: an engineer may well inspect the described workers first and find that they cannot read the queues they are named for. The key's reading is taken because the README names this divergence between descriptions and graph as a deliberate trap and makes the graph the source of truth for what is connected, which is also the conventions' rule; a reader who holds the other reading should read this verdict as the key's reading kept, as in the storefront entry. The fulfillment queues have no redrive, so no dead-letter queue joins the set.
